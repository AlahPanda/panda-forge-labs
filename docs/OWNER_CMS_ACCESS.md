1. No [Supabase Dashboard Preview](https://supabase.com/dashboard/project/jnvckqlschyquzzfldrs), confirma o ref `jnvckqlschyquzzfldrs`. Em **Edge Functions**, verifica que existe `admin-cms`, anota o endpoint `https://jnvckqlschyquzzfldrs.supabase.co/functions/v1/admin-cms` e confirma `verify_jwt = false`. A função valida o seu JWT administrativo próprio. Uma resposta de erro a pedido anónimo pode ser normal; não a confundas com login operacional.

O antigo `ADMIN_ORIGIN` continua a funcionar apenas quando `ADMIN_ORIGINS` não está definido. Quando `ADMIN_ORIGINS` existe, substitui a configuração antiga por completo. Não uses `*`, `*.vercel.app`, paths ou o domínio Production.

## Troca/recuperação

Se esqueceres a password, inicia sessão no **dashboard Supabase de Preview** como proprietário e substitui `ADMIN_PASSWORD` em **Edge Functions → Secrets** por uma nova. Atualiza `ADMIN_JWT_SECRET` para invalidar sessões existentes (em todos os browsers). Espera os secrets propagarem, recarrega `/admin`, inicia sessão com a nova password. Tokens ficam em `sessionStorage` e são retirados ao terminar sessão; sessões antigas também são rejeitadas assim que o JWT secret mudar. Não é necessário recuperar nem imprimir a password antiga.

Sem `ADMIN_PASSWORD`, `ADMIN_JWT_SECRET` ou uma configuração base válida `ADMIN_ORIGINS`/`ADMIN_ORIGIN` a função falha fechada; nunca usa credenciais default. A password não deve ser pedida nem introduzida nesta conversa. Ver documentação oficial: [Edge Function secrets](https://supabase.com/docs/guides/functions/secrets) e [deploy e chave publicável](https://supabase.com/docs/guides/functions/deploy).

## Diagnóstico operacional e publicação

O endereço estável redirecionou o browser externo para **Vercel Authentication antes de `/admin`** na verificação desta fase. Isto é proteção da Vercel, distinta da password CMS. Não foi contornada nem foi verificada a sessão Vercel do proprietário; o teste real de login continua pendente. No teu browser autenticado na equipa Vercel, abre o alias acima seguido de `/admin`; não uses URLs únicas por deployment. Se também obtiveres o login Vercel, abre **Vercel → projeto AlahPanda Labs → Settings → Deployment Protection** e verifica que a tua conta tem acesso à proteção de Preview. Não desligues a proteção para este teste.

Erros distinguidos: origem recusada **pela Edge** (403), password inválida (401), ausência de configuração Supabase/Edge, sessão expirada (401), falha de acesso GitHub no Editor e falha de rede. A resposta 403 da Edge regista `receivedOrigin` e `expectedOrigins` sem revelar segredos, e nunca devolve `Access-Control-Allow-Origin` à origem recusada. **Por isso o browser dessa origem pode apresentar erro CORS como falha de rede**, sem conseguir ler o 403. O login mostra a origem que o browser utilizou, o alias preferido (se configurado) e onde conferir o deploy/configuração Edge. Uma origem diferente do alias não é bloqueada localmente. A Edge aceita origens exatas configuradas, `ADMIN_PREVIEW_ALIAS` opcional e apenas o hostname gerado para este projeto e scope; não aceita qualquer subdomínio Vercel.

O fluxo do Editor distingue **Draft → Previewed → Committed to Preview → Preview Ready → Live/Production**. `draft-publish` grava na branch `v2/full-redesign` e devolve o SHA do commit; isto **não comprova um deployment**. O build Vercel inclui `/preview-build.json` com `VERCEL_GIT_COMMIT_REF` e `VERCEL_GIT_COMMIT_SHA` públicos. O painel só reconhece *Preview Ready* quando a origem em uso ou o alias preferido devolve JSON com esta branch e o SHA exato do commit; se a Vercel exigir sessão, a verificação pode continuar pendente e existe botão para voltar a verificar. Não existe promoção automática a Production e o painel não a declara para esta branch. A verificação identifica o build, mas o proprietário deve confirmar o conteúdo atualizado na rota pública.

**Teste manual pendente na conta do proprietário**, depois de as variáveis/secrets terem sido confirmados e o Preview novo estar pronto: 1) abre o alias `/admin` e entra; 2) confirma o redirecionamento para `/admin/editor` e a leitura de Content V2; 3) cria um draft privado de conteúdo editorial aprovado e confirma que não aparece numa janela pública; 4) abre a pré-visualização privada; 5) confirma `GITHUB_REPO` e `GITHUB_BRANCH`, publica conscientemente; 6) confere o commit em `v2/full-redesign` e o deployment correspondente em **Vercel → Deployments**, com filtro Preview/branch; 7) no alias, usa «Retry» para verificar o SHA e abre a rota pública para conferir o conteúdo real; 8) confirma que Production não mudou.
