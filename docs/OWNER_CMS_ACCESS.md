# Acesso do proprietário ao CMS (Preview V2)

## Antes de configurar

`/admin` é a única entrada de login; após autenticação, abre `/admin/editor`. Não existe password por defeito. A função `supabase/functions/admin-cms/index.ts` compara a string enviada com **`ADMIN_PASSWORD`**, guardada em secrets server-side do projeto Supabase. Atualmente não utiliza hash: introduz a nova password diretamente como valor do secret. O browser nunca recebe o valor do secret. Não é possível descobrir a password anterior a partir do repositório.

**Projeto isolado de Preview:** ref `jnvckqlschyquzzfldrs`, URL `https://jnvckqlschyquzzfldrs.supabase.co`. O project ref histórico `ypfxaqqilqnbpxbttngy` não é Preview e nunca deve ser selecionado para esta fase. No rows returned`; confirmar a presença de `public.cms_drafts` em **Database → Table Editor**. Os secrets Edge são partilhados por função no mesmo projeto: confirmar sempre o ref antes de editar.

## Configuração pelo proprietário

1. No [Supabase Dashboard Preview](https://supabase.com/dashboard/project/jnvckqlschyquzzfldrs), confirma o ref `jnvckqlschyquzzfldrs`. Em **Edge Functions**, verifica que existe `admin-cms`, anota o endpoint `https://jnvckqlschyquzzfldrs.supabase.co/functions/v1/admin-cms` e confirma `verify_jwt = false`. A função valida o seu JWT administrativo próprio. Uma resposta de erro a pedido anónimo pode ser normal; não a confundas com login operacional.
2. Abre **Edge Functions → Secrets** desse projeto. Cria ou atualiza a chave **`ADMIN_PASSWORD`** com uma **nova password longa e única, escolhida agora**, diretamente no campo Value; guarda. Não utilizes uma password escrita em conversas anteriores, código, documentação, `VITE_*` ou logs. O valor é plaintext **dentro do secret server-side**, porque é isso que o código atual compara; não coloques um hash neste campo.
3. No mesmo projeto, configura **`ADMIN_JWT_SECRET`** com um segredo aleatório independente da password (por exemplo, gerado num gestor de passwords). Rodá-lo invalida todos os tokens anteriores; mudar só `ADMIN_PASSWORD` impede novos logins com a password antiga, mas tokens já emitidos continuam válidos até expirarem (máximo oito horas).
4. Em **Vercel → projeto AlahPanda Labs → Deployments**, filtra pela branch `v2/full-redesign` e abre o Preview. Copia a **origem HTTPS estável da branch** (por exemplo, domínio de branch atribuído ao projeto), sem path nem `/` final. Verifica a origem na barra do browser; URLs únicas por commit podem mudar. Configura este valor em **`ADMIN_ORIGIN`** no Supabase Preview. A função rejeita outras origens e não aceita `*` nem múltiplas origens hoje. Se não existir um endereço estável, atribui primeiro um domínio Preview específico à branch em Vercel; não uses o domínio de Production.
5. Para publicação no repositório de Preview, configura **`GITHUB_REPO=AlahPanda/panda-forge-labs`** e **`GITHUB_BRANCH=v2/full-redesign`**, além de **`GITHUB_TOKEN`** com a autorização necessária. A função faz todas as escritas GitHub; o token permanece server-side. Deixa `VERCEL_DEPLOY_HOOK` vazio se não existir um hook estritamente isolado para Preview. Não testes publicação antes de confirmar estes destinos.
6. A função de drafts requer `SUPABASE_URL` e `SUPABASE_SERVICE_ROLE_KEY` server-side e a tabela/migração `cms_drafts`. Consulta `supabase/migrations/` e `docs/V2_PHASE_3A.md`. Os nomes `SUPABASE_*` são normalmente injetados pelo Supabase remoto; confirma que estão disponíveis no projeto e **não tentes criar manualmente uma chave reservada** no dashboard de secrets. Nunca coloques a service role num `VITE_*`.
7. Em **Vercel → projeto AlahPanda Labs → Settings → Environment Variables**, seleciona **Preview** e, se disponível, filtra especificamente pela branch `v2/full-redesign`; confirma que **Production não está selecionado**. Define `VITE_SUPABASE_URL=https://jnvckqlschyquzzfldrs.supabase.co` e `VITE_SUPABASE_PUBLISHABLE_KEY` com a **publishable key** do mesmo projeto Supabase em **Project Settings → API Keys**. Não copies a secret/service role key. Após alterar variáveis Vite, cria **um novo deployment Preview da branch** (em Deployments → último Preview da branch → Redeploy com ambiente Preview, ou novo commit na branch). Nunca uses Promote to Production nem `vercel --prod`.
8. Abre `<origem-do-preview>/admin`. Introduz a nova password escolhida no passo 2. Confirma o redirecionamento para `/admin/editor` e que a sessão carrega o Dashboard. Um pedido de publicação de teste grava na branch configurada; não o faças sem confirmar antes `GITHUB_BRANCH` e eventual deploy hook.

## Troca/recuperação

Se esqueceres a password, inicia sessão no **dashboard Supabase de Preview** como proprietário e substitui `ADMIN_PASSWORD` em **Edge Functions → Secrets** por uma nova. Atualiza `ADMIN_JWT_SECRET` para invalidar sessões existentes (em todos os browsers). Espera os secrets propagarem, recarrega `/admin`, inicia sessão com a nova password. Tokens ficam em `sessionStorage` e são retirados ao terminar sessão; sessões antigas também são rejeitadas assim que o JWT secret mudar. Não é necessário recuperar nem imprimir a password antiga.

Sem `ADMIN_PASSWORD`, `ADMIN_JWT_SECRET` ou `ADMIN_ORIGIN` a função falha fechada; nunca usa credenciais default. A password não deve ser pedida nem introduzida nesta conversa. Ver documentação oficial: [Edge Function secrets](https://supabase.com/docs/guides/functions/secrets) e [deploy e chave publicável](https://supabase.com/docs/guides/functions/deploy).

## Deploy da função e renovação do acesso

O workflow `.github/workflows/deploy-supabase-preview.yml` escuta **push apenas em `v2/full-redesign`** quando mudam a função, `supabase/config.toml` ou o próprio workflow. Recusa correr se o repository secret `SUPABASE_PROJECT_ID` não for exatamente `jnvckqlschyquzzfldrs`. O comando usa sempre `supabase functions deploy admin-cms --project-ref jnvckqlschyquzzfldrs`. O GitHub só mostra o botão manual Run workflow para workflows que existam na default branch; **não o coloques em `main`** para contornar essa limitação. Confirma em **GitHub → Actions → Deploy Supabase Preview Function** se a execução terminou bem; depois confirma a função em Supabase Preview. O deploy usa o código completo do repositório, incluindo imports e `verify_jwt = false` em `supabase/config.toml`.

O GitHub repository secret `SUPABASE_ACCESS_TOKEN` é um token Supabase de acesso limitado ao projeto Preview e Edge Functions; o proprietário indicou prazo de sete dias. Antes da expiração, cria no dashboard Supabase um novo scoped access token com o mesmo âmbito, atualiza **GitHub → repositório → Settings → Secrets and variables → Actions → Repository secrets → `SUPABASE_ACCESS_TOKEN`**, revoga o antigo e executa um novo push controlado na branch que altere a função/config/workflow para testar. Não publiques nem imprimas o token. `SUPABASE_PROJECT_ID` deve manter o ref Preview; se alterar, o workflow falha fechado.

## Verificação privada sem publicar

Após a configuração, visita o Preview `/admin` e entra com a password definida diretamente no dashboard. Confirma `/admin/editor`, refresh da sessão e logout. Sem sessão, `/admin/editor` deve voltar ao login. Cria no CMS um draft de teste identificado como descartável; confirma **Supabase Preview → Database → Table Editor → `public.cms_drafts`** e a revisão incremental, lê a pré-visualização privada e apaga o draft. Não carregues em Publish nem uses a ação Redeploy do CMS nesta verificação. O browser público não recebe a service role; a tabela tem RLS ativo e não concede acesso `anon`/`authenticated`.

## Estado de validação

O repositório não mostra o estado dos secrets remotos nem comprova o login real. Ver `V2_PREVIEW_INFRASTRUCTURE.md` para separar claramente o que foi confirmado do que continua pendente. Os testes automatizados cobrem falha por falta de configuração, rejeição de password errada, autenticação simulada, guard e redirecionamento no cliente.
